# SpactVault review: useful patterns for Bouncer

Source inspected on 2 November 2026: [SpactVault at `27e9655`](https://github.com/0xileri/SpactVault/tree/27e9655611bf5c42cf5cec741b2c43ee04a94073). This is a source review, not an independent test or audit. SpactVault describes itself as unaudited. Its README contains both a local-sandbox-only warning and descriptions of testnet and small mainnet deployments; deployment details have not been independently verified here. We found no repository license, and GitHub's license endpoint returned 404. Do not copy its code or assets without appropriate permission; the changes described below are independently implemented in Bouncer.

## What is useful

1. **Make exact owner approval understandable.** SpactVault's [request flow](https://github.com/0xileri/SpactVault/blob/27e9655611bf5c42cf5cec741b2c43ee04a94073/docs/ARCHITECTURE.md) shows the token, amount, recipient, expiry, agent and policy context, then asks the owner to approve the request hash. Its [contract digest](https://github.com/0xileri/SpactVault/blob/27e9655611bf5c42cf5cec741b2c43ee04a94073/contracts/spact-vault/src/digest.rs) binds those terms to the vault, network and policy version. Bouncer already has V11 exact-FT intents, revision locks, expiry and the 1-yocto owner guard, but its on-chain `review_hash` is an opaque value supplied with the separate terms; the contract does not recompute that hash from a review document. A future owner UI should independently reconstruct and display the original reviewed terms, verify the retained commitment and show the actual wallet call. Keep Svalin bearer codes out of links and views. A future vault version could consider an on-chain canonical request digest, without weakening the rolling limits or owner guard; the existing keyless V11 deployment cannot be upgraded.

   **Applied now:** Bouncer's shared exact-FT verifier checks that the MultiAgency and Svalin Pro review documents actually correspond to the submitted token, payee, amount, memo, cutoff and derived intent ID before preflight or payment-evidence verification. Unknown review protocols fail closed. Adversarial local tests cover mismatches even where the review is rehashed. This is off-chain defense in depth, not a change to the deployed contract: a wholly new, internally consistent review can still pass unless the caller reconstructs it from the original trusted goal/reservation and compares it with the retained original commitment. It does not authenticate the seller or prove owner approval, payment or delivery.

2. **Make security evidence navigable, not overstated.** SpactVault's [Security Lab catalog](https://github.com/0xileri/SpactVault/blob/27e9655611bf5c42cf5cec741b2c43ee04a94073/packages/security-lab/src/catalog.ts) organizes attack scenarios and test evidence. A Bouncer equivalent could map policy escalation, cap/allowlist bypass, callback refunds, intent substitution and replay to named tests and original on-chain receipts. Label synthetic, local-chain, live testnet and independent fulfillment separately; skipped, unavailable or stale evidence must never be shown as a pass, and no test report is a security audit.

3. **Restricted-key checks are useful for a later MCP write path.** SpactVault documents a [local MCP preflight](https://github.com/0xileri/SpactVault/blob/27e9655611bf5c42cf5cec741b2c43ee04a94073/apps/mcp/src/agentKey.ts) for the network, agent and function-call key. Bouncer already checks scoped keys in payment runners; its existing [MCP server](../mcp/server.mjs) is deliberately read-only and does not load credentials or pay. If a write-capable MCP is built later, reuse Bouncer's existing scoped-key checks, original-hash journal and trusted-owner boundaries; never accept a full-access key from an MCP client. MCP expansion remains secondary to getting the core multi-resource path working.

## What it does not solve

SpactVault is another spending-policy vault, not a discovered independent compute, storage or data provider. Its documented testnet demo uses its own test token and payee. It does not establish Circle-test-USDC paid fulfillment for Bouncer or bridge the current V11 keyless vault to Svalin's x402 `exact` scheme. Its on-chain budget is based on UTC days, whereas Bouncer's rolling budget is a separate design. Replacing Bouncer's vault would not automatically preserve Bouncer's refund accounting, 1-yocto owner-policy primitive, resource adapters or replay/recovery guarantees.

**Priority:** keep pursuing a real, independently operated FT-paid resource and original-hash recovery. The approval and evidence ideas support that goal; they are not a reason to pivot away from the multi-resource agent or to claim the independent-provider gap is closed.
